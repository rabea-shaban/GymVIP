# Backend audit

Audit date: 2026-11-11. Scope: the accessible Express routes, controllers, services, middleware, validators, jobs, Prisma schema and associated client call sites. All findings below are **VERIFIED IN CODE**, except explicitly marked concurrency outcomes (**SUSPECTED**, requiring an isolated MySQL test). No business data was changed. Runtime/test results are recorded separately in report 11; a mocked database test does not establish persistence or database concurrency correctness.

## Assessment

The backend is a substantial implementation, not a mock API. Fifteen route modules use controllers and services with Prisma persistence, tenant scoping, DTOs, role restrictions and Zod validation. Working foundations include immutable subscription price snapshots, Decimal payment arithmetic, cancellation compare-and-set, transactional trainer creation, notification deduplication, and safe audit-data serialization. Do not rebuild these foundations.

Backend quality: **55/100**, a code-based readiness score: structure/contracts 17/20; access boundaries 12/20; lifecycle/business correctness 8/25; validation/error handling 10/15; concurrency/operability 8/20. This is not a percentage of endpoints proven operational. Primary deductions are the concrete lifecycle, identity and authorization defects below.

## HTTP and authorization conventions

Successful mutation creation generally returns 201; reads/updates return 200; `AppError` maps authentication 401, role 403, missing entity 404, conflicts 409. Zod errors return 400. Unknown errors return 500 with stack suppressed in production. Some generic Prisma errors are mapped to 400 regardless of server/client cause. Production generic error logging is incomplete because initial logging is disabled in production (`Backend/src/middlewares/error.middleware.ts:17`).

All business modules use `requireAuth`; it loads current user/gym from DB rather than trusting JWT roles. Health, registration/login and cookie-clearing logout are public by design. Tenant IDs come from auth context, not payload. Most ID reads include gymId and most mutations first verify ownership. This is good isolation groundwork, not proof every future query is safe. No duplicate same-method/same-path route was found. Both attendance-ID and member-ID checkout are intentional alternative endpoints.

Role key: O = OWNER, M = MANAGER, R = RECEPTIONIST, T = TRAINER; ALL = all four authenticated roles. There is no SUPER_ADMIN, ACCOUNTANT or MEMBER role. Individual service restrictions apply in addition to route gates (manager cannot manage owner/manager via user APIs; trainer can read only its own trainer profile). Reports other than payments and dashboard are ALL with financial fields suppressed for R/T; training-specific member assignments do not exist, so member read access is tenant-wide.
